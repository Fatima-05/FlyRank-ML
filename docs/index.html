Ranking Pages for Content Refresh: A Learned Opportunity Score vs a Hand-Written Rule

FlyRank ML Internship Capstone · Fatima-Tu-Zahra

Abstract

Small content teams need a short list of which pages to refresh first. This project uses anonymized page-level search and content signals from the FlyRank ML Internship dataset. A hand-written baseline rule is compared to tree-based models on the same client-holdout split, using Precision@50. On this run, random forest reaches 0.62 Precision@50 versus 0.50 for the baseline (decision tree 0.42). The output is a ranked action queue with scores, actions, and reason codes for human review, not auto-publish.

1. Introduction / Problem

A content team often has more pages than review time. Choosing what to refresh first is usually informal. This project supports one decision: given page-level signals, which pages should enter the next refresh queue first? The goal is a short ranked list a person can act on, not a full site audit and not a claim about any search engine’s ranking algorithm.

  • Unit of analysis: one content item (page)
  • Output: ranked queue with score, action, and reason codes
  • Human action: review the top of the queue and refresh or monitor within capacity
  • Cost of a wrong call: wasted editor time or missed high-demand aging pages

2. Data

Source: FlyRank ML Internship dataset (starter page-level table and warehouse access pattern used across the track). Reproducible comparison table: data/raw/content_refresh_anonymized.csv (~30,000 rows).

Excluded from public outputs and model features: client names, domains, URLs, private queries, credentials, and label shortcuts such as using trend_direction as a model feature or inside the baseline score. Pseudonymous IDs are used only for grouping/splitting and display, never as predictive features.

3. Methodology

  • Task: ranking / opportunity scoring
  • Proxy label: is_declining = 1 when trend_direction is down
  • Baseline: hand-written score on non-label signals only (impressions, age, CTR, position, thinness)
  • Models: decision tree and random forest, ranked by positive-class probability
  • Features: impressions_90d, clicks_90d, ctr, content_age_days, word_count, avg_position, search_volume
  • Validation: GroupShuffleSplit on client_id (25% test, random_state=42)
  • Metric: Precision@50 on the held-out set

5. Limitations

This is offline decision support. It does not prove that refreshing a flagged page causes traffic gains, does not treat the proxy label as confirmed editorial truth, and does not report live team adoption. Results are directional and measured on one holdout design.

6. Ranked recommendations

  1. Sort by model score descending
  2. Review the top of the queue first
  3. Use reason codes (high impressions, low CTR, aging, striking distance) to understand each flag
  4. Cap weekly capacity (example: top 8–10)
  5. Human makes the final call — the queue is a reviewer aid, not auto-publish
